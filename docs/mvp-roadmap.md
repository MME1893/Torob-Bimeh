# نقشهٔ راه ترب بیمه — نسخهٔ قابل بازبینی

## پیشرفت ۲۴ سپتامبر ۲۰۲۶

اولین برش انتهابه‌انتها با فرم React/TypeScript، `POST /api/search`، نگاشت صریح پژو پارس شخصی و حفظ JSON کامل سه منبع اجرا شد. سابیم برای شاخهٔ بدون بیمهٔ قبلی وضعیت `needs_input` می‌دهد؛ برای دیگر مدل‌ها `unmapped` و برای محصولات بعدی `unsupported` بازمی‌گردد. قیمت‌ها هنوز واحد تأییدشده ندارند و وارد رتبه‌بندی نمی‌شوند. آزمون‌های یکپارچه با پاسخ شبیه‌سازی‌شده‌اند؛ استعلام زندهٔ این برش در این محیط تأیید نشده است. بخش «وضعیت واقعی زیرساخت» در ادامه، خط مبنای قبل از این برش را شرح می‌دهد.

## تصمیم محصول

MVP سه مسیر دارد: **شخص ثالث خودرو، بدنهٔ خودرو و شخص ثالث موتور**. یک فرم فارسی و راست‌چین با شاخه‌های شرطی برای این سه مسیر ساخته می‌شود. هر جست‌وجو درخواست‌های واقعی را برای چهار منبع ازکی، سابیم، بیمه‌بازار و بیمه‌دات‌کام اجرا می‌کند؛ خروجی هر منبع مستقل موفق، خالی یا خطادار گزارش می‌شود. بدنهٔ موتور در این نسخه وارد جست‌وجوی واحد نمی‌شود. نمونهٔ تاریخی HAR هرگز به‌عنوان قیمت همان لحظه عرضه نمی‌شود.

آزمایشگاه‌های HTML فعلی تا پایان کار برای آزمودن آداپتورها باقی می‌مانند. رابط اصلی جدید از داده و شناسهٔ خام یک سایت برای ساخت درخواست سایت دیگر استفاده نمی‌کند.

## وضعیت واقعی زیرساخت

| بخش | امروز | کاری که مانده است |
| --- | --- | --- |
| درخواست به چهار سایت | روتر و کلاینت مستقل برای سه محصول وجود دارد | تبدیل فرم مشترک به ورودی هر روتر؛ شناسه‌ها برای هر سایت متفاوت‌اند |
| پاسخ ازکی | ثالث: `company.prices[]`؛ بدنه: `company.price`/`discountedPrice` | نرمال‌سازی قیمت، مدت، پوشش و شرکت |
| پاسخ بیمه‌بازار | `data.offers[]` و `tariff` | نرمال‌سازی و بررسی واحد مبلغ |
| پاسخ بیمه‌دات‌کام | `Inquiries[]`، `Companies[]` و `CashPrice.FinalAmount` | پیوند شناسهٔ شرکت و تأیید واحد مبلغ |
| پاسخ سابیم | روتر ارسال دارد؛ نمونه‌های ضبط‌شدهٔ بدنه `500` بوده‌اند | ثبت نمونهٔ موفق هر محصول و نوشتن پارسر؛ خطا به کاربر نشان داده شود |

بنابراین «اتصال آداپتور» تکمیل شده، اما **کاتالوگ مشترک، مبدل ورودی، نرمال‌ساز خروجی و API جست‌وجوی واحد** هنوز ساخته نشده‌اند. بعضی پاسخ‌ها عدد خام دارند؛ تا تأیید ریال/تومان، قیمت مشترک و رتبه‌بندی بر پایهٔ آن نشان داده نمی‌شود.

## قرارداد فرم واحد

قرارداد پایه در `backend/app/domain/quotes.py` تعریف شده است. `SearchInput` یک union با شاخه‌های `third_car`، `body_car` و `third_motor` است؛ این schema هنوز به مسیر API عمومی وصل نشده است. کلیدهای `brand_key`، `model_key`، `motor_type_key` و مانند آن، کلیدهای داخلی کاتالوگ آینده‌اند و شناسهٔ هیچ‌یک از سایت‌ها نیستند.

| مرحلهٔ فرم | ثالث خودرو | بدنهٔ خودرو | ثالث موتور |
| --- | --- | --- | --- |
| وسیله | دسته، برند، مدل، کاربری، سال ساخت | همان‌ها + ماه ساخت، داخلی/وارداتی، سوخت در صورت نیاز | نوع موتور و سال ساخت |
| بیمهٔ قبلی | وضعیت، شرکت، تاریخ شروع/انقضا، مدت، تخفیف ثالث/راننده، خسارت، تغییر مالکیت | داشتن بیمهٔ بدنه، شرکت و تاریخ قبلی، سابقهٔ بدون خسارت؛ شرکت و تخفیف ثالث | شاخه‌های وضعیت و سابقهٔ ثالث مانند خودرو |
| پوشش و قیمت | مدت درخواست و سقف تعهد مالی | ارزش روز خودرو، ارزش لوازم، شهر/استان و پوشش‌های انتخابی | مدت درخواست و سقف تعهد مالی |

فقط فیلدهای شاخهٔ فعال پرسیده شوند؛ فیلدهایی مانند «شرکت بیمهٔ قبلی» برای کاربری که بیمهٔ قبلی ندارد نمایش داده نشوند. تاریخ را به کاربر شمسی نشان می‌دهیم و در DTO با ISO میلادی نگه می‌داریم؛ تبدیل و نگاشت سال/ماه برای هر منبع آزمایش می‌شود. قیمت ورودی کاربر **تومان** است و تغییر واحد برای API هر سایت در مبدل همان سایت انجام می‌شود. نام‌گذاری یکسان به معنی شناسهٔ یکسان نیست: هر برند/مدل/پوشش باید جدول نگاشت مستقل و موارد نامشخص باید وضعیت `unmapped` بگیرند.

## قرارداد نتیجه و رفتار API

`POST /api/search` پس از تکمیل نگاشت‌ها ساخته می‌شود: یک `SearchInput` می‌گیرد و `SearchResult` شامل `ProviderResult` هر چهار سایت برمی‌گرداند. Backend درخواست‌ها را موازی و با مهلت جداگانه اجرا می‌کند. شکست یک منبع جلوی پیشنهادهای منابع دیگر را نمی‌گیرد. وضعیت‌های `ok`، `empty`، `needs_input`، `unmapped`، `unavailable` و `unsupported` با علت کوتاه در UI دیده می‌شوند.

هر `Offer` منبع، شرکت، مبلغ خام، واحد مبلغ خام (`toman`/`rial`/`unknown`)، مبلغ تأییدشدهٔ تومان در صورت وجود، مدت، سقف و پوشش‌های قابل‌تأیید، زمان دریافت و لینک صفحهٔ مقایسه دارد. در صورت نامعلوم بودن واحد، `amount_toman` خالی می‌ماند و آن نتیجه وارد مرتب‌سازی «ارزان‌ترین» میان منابع نمی‌شود. دو پیشنهاد فقط با **محصول، مدت و سقف/شرایط قابل‌مقایسه** کنار هم رتبه‌بندی می‌شوند؛ تخفیف و اقساط جدا نشان داده می‌شوند.

**هیچ فیلد پاسخ حذف نمی‌شود:** `ProviderResult.raw_response` کل JSON دریافتی همان سایت را در فضای مجزای نام همان منبع نگه می‌دارد و `Offer.raw_offer` ردیف اصلی پیشنهاد را برای نمایش جزئیات کارت نگه می‌دارد. فیلدهای مشترک برای مرتب‌سازی و مقایسه‌اند؛ JSON خام هر منبع برای بررسی و دانلود در فرانت قابل باز کردن است. منظور از «خام» فقط بدنهٔ پاسخ API است، نه هدرهای حاوی توکن یا کوکی. برای چت AI تنها بخش‌های مرتبط و معتبر DTO به مدل داده می‌شود تا دادهٔ حجیم خام یا اطلاعات اضافی وارد prompt نشود.

## تجربهٔ کاربر

1. صفحهٔ آغاز: سه کارت تصویری برای نوع بیمه، توضیح کوتاه دربارهٔ «یک بار اطلاعات، مقایسهٔ چند منبع»، ورود به گفت‌وگوی راهنما یا کمک گرفتن از AI.
2. ورود اطلاعات در گفت‌وگویی کوتاه: وسیله ← بیمهٔ قبلی ← پوشش/ارزش ← مرور و تأیید. هر نوبت یک سؤال روشن همراه انتخاب‌های بصری، جست‌وجوی مدل، کنترل عدد/تاریخ و خلاصهٔ پاسخ‌های قبلی است؛ همان ورودی‌های ساختاریافتهٔ DTO پشت تجربه حفظ می‌شوند. در موبایل یک ستون؛ اعتبارسنجی کنار همان سؤال؛ امکان برگشت بدون پاک شدن پاسخ‌ها.
3. وضعیت جست‌وجو: چهار نشانگر مجزا؛ پیشنهادهای رسیده زودتر نمایش داده می‌شوند و خطای هر سایت جداست. در نسخهٔ اول اگر streaming پیچیدگی ایجاد کند، یک پاسخ تجمیعی با وضعیت هر منبع کافی است.
4. نتایج: تعداد منابع موفق، زمان استعلام، فیلتر شرکت/اقساط/پوشش، مرتب‌سازی قیمتِ دارای واحد تأییدشده، کارت با قیمت، شرایط و لینک صفحهٔ مقایسهٔ همان سایت. پنل «چرا این پیشنهاد؟» محدود به داده‌های واقعی همان کارت.
5. برند و حرکت: لوگوی سه‌برگ تأییدشدهٔ ترب بیمه با همان نوشتار حفظ شود؛ از آن نشانک کوچک استخراج شود. کارت تصویری خودرو/موتور با SVG اختصاصی، حرکت کوتاه در ورود کارت‌ها و وضعیت بارگذاری هر منبع؛ برای `prefers-reduced-motion` حرکت حذف شود. زمان انتظار و حرکت تزئینی با هم اشتباه گرفته نشوند.

### جهت بصری منتخب برای طراحی

پیشنهاد کاربر: **«Design a visual storytelling, friendly fintech onboarding experience for Torob Bimeh with image-based insurance selection (maybe using animation too) and a simple conversational flow instead of a traditional form.»** این مسیر جست‌وجومحورِ ترب را با روایت تصویری ترکیب می‌کند. چیدمان اولیه با مشورت کاربر مشخص شد: **سه کارت تصویری، سپس پرسش‌های گفت‌وگویی در همان صفحه**. گزینه‌ها و جزئیات قابل بازبینی در [ui-concepts.md](ui-concepts.md) آمده‌اند.

## دو نقش AI

- **قبل از ارسال:** گفت‌وگو داده‌های مورد نیاز را سؤال می‌کند و فقط یک **پیش‌نویس تایپ‌شدهٔ همان `SearchInput`** می‌سازد. فیلد نامطمئن یا ناموجود مشخص است؛ کاربر پیش‌نمایش را می‌بیند و ارسال واقعی را تأیید می‌کند. مدل اجازه ندارد شناسهٔ برند یا پوشش را حدس بزند؛ انتخاب نهایی از کاتالوگ معتبر است.
- **بعد از نتایج:** چت و خلاصه به `SearchResult` همان جست‌وجو محدودند. هر ادعای قیمت/پوشش/شرکت باید به شناسهٔ پیشنهاد، منبع و زمان دریافت اشاره کند؛ قیمت با واحد نامشخص و منابع خطادار در پیشنهاد «بهترین قیمت» وارد نشوند. خروجی AI جایگزین قواعد قطعی رتبه‌بندی نیست.

کلید مدل فقط در Backend قرار می‌گیرد. اگر کلید وجود نداشت، فرم و مقایسه بدون چت همچنان کار می‌کنند. مسیرهای پیشنهادی `POST /api/assistant/intake` و `POST /api/assistant/results` هستند؛ قرارداد پاسخ و عمر دادهٔ جست‌وجو پیش از اتصال مدل نهایی می‌شود.

## ترتیب اجرا و شرط پایان هر گام

| گام | خروجی قابل بازبینی | شرط عبور |
| --- | --- | --- |
| ۱. قرارداد و کاتالوگ | DTOهای ورودی/خروجی، جدول شناسه‌ها برای هر منبع، تطبیق نمونه‌های شناخته‌شده | هیچ شناسهٔ تأییدنشده‌ای خودکار برای سایت دیگر ارسال نشود |
| ۲. برش عمودی ثالث خودرو | `POST /api/search` با مبدل ورودی و پارسر خروجی چهار منبع، وضعیت مستقل | فرم واحد یک سناریوی واقعی را اجرا کند؛ یک منبع خطادار نتیجهٔ سه منبع دیگر را حذف نکند |
| ۳. رابط پایه | پروژهٔ React + TypeScript + Vite، صفحهٔ محصول، فرم مرحله‌ای و نتایج RTL | همان سناریوی ثالث خودرو از فرم تا کارت و لینک مقصد کار کند |
| ۴. گسترش محصول | بدنهٔ خودرو و ثالث موتور، پوشش‌ها و شاخه‌های شرطی | سناریوهای شناخته‌شدهٔ HTML با DTO و سایت مبدا همخوانی داشته باشند |
| ۵. مقایسه و AI | تأیید واحد و شرایط، رتبه‌بندی شفاف، گفت‌وگوی قبل/بعد | AI هیچ داده یا مبلغی خارج از DTO و پیشنهادهای دریافتی نسازد |
| ۶. پرداخت UX و دمو | آیکون، انیمیشن سبک، موبایل، دسترس‌پذیری، ویدیوی کوتاه از محصول واقعی | نمایش درخواست واقعی، خطای یک منبع، دلیل انتخاب و دو نقش AI در دمو |

پس از گام ۱، گام‌های ۲ و ۳ را به صورت **برش‌های انتهابه‌انتها** جلو می‌بریم: اتصال یک محصول واقعی در Backend، سپس UI همان محصول، سپس گسترش دامنه. ساختن تمام صفحات فرانت قبل از نگاشت شناسه‌ها، فرم زیبایی می‌سازد که لزوماً دادهٔ درستی به چهار منبع نمی‌فرستد.

### بیرون از MVP

خرید و صدور بیمه، پرداخت، حساب کاربری، ذخیرهٔ اطلاعات شخصی، بدنهٔ موتور، امتیازدهی بدون منبع به شرکت‌ها، قیمت ساختگی، و مقایسهٔ اعداد با واحد نامعلوم. گزارش HTML/HAR تاریخی فقط برای آزمون قرارداد می‌ماند، نه کارت زندهٔ کاربر.

### انتخاب فنی

FastAPI موجود حفظ می‌شود؛ [مدل پاسخ FastAPI](https://fastapi.tiangolo.com/tutorial/response-model/) با Pydantic قراردادها را برای مستندات و اعتبارسنجی API نگه می‌دارد. [React + TypeScript + Vite](https://vite.dev/guide/) برای فرم شرطی و نتایج تعاملی استفاده می‌شود. در توسعه، `/api` از Vite به FastAPI proxy می‌شود؛ در دمو UI و API با یک مبدأ سرو می‌شوند. نسخهٔ اول بدون پایگاه داده و با تنظیمات و کلیدها در Backend اجرا می‌شود؛ ذخیرهٔ تاریخچه به نسخهٔ بعد موکول است.
